# Failure Mode Selection

The user opens the page from **Response > Failure Mode Selection**. It lists every PFM that DST covers, grouped by the part of the dam and the
loading, with DST's recommendation and the team's decision for each. <FigReference figKey="dst-users-guide-fig-failure-mode-selection-page" /> shows
the page, and <TableReference tableKey="dst-users-guide-table-failure-mode-screening-and-selection-selection-regions" /> describes each numbered region.

The information icon on each column heading explains the column and its symbols. On phones, the DST recommendation moves above each failure mode's
name and the status below it.

## Groups and failure modes

The groups are **Earth Embankment — Flood**, **Earth Embankment — Seismic**, **Spillway — Flood**, **Concrete Dam — Flood**, **Concrete Dam —
Seismic** and **User Defined**. Each row names its failure mode by number and name, for example **01 - Embankment Overtopping Erosion**.

- A group heading reads "Not applicable" with a reason, such as "No concrete dam type in Dam Data", when the dam has nothing it applies to. A single
  failure mode can also be marked **N/A**; resting the pointer on it gives the reason, such as "No conduit recorded in Dam Information".
- A failure mode that DST cannot yet evaluate reads **Coming soon**; resting the pointer on it gives the reason, "DST does not have an evaluation
  workflow for this failure mode yet."

Neither kind takes a decision.

## Recommendations

The **DST** column shows DST's recommendation as a pill. <TableReference tableKey="dst-users-guide-table-failure-mode-screening-and-selection-recommendations" />
lists the recommendations. Resting the pointer on a pill shows "Screening recommendation: Evaluate" or "Exclude", "Your decision overrides it: Exclude" (or Evaluate) when the team's decision differs,
and a note on what led to the recommendation, including how any Unknown answers were treated.

The first time a firm Evaluate or Exclude recommendation appears for a failure mode, DST sets the team's decision to match it. After that, DST never
changes a decision; it flags the change instead (see [Recommendation changes](#recommendation-changes)).

## Decisions

The **Evaluate** toggle records the team's decision. On (blue row) means the failure mode is evaluated and carries on to the Failure Mode Evaluation
page; off means it is excluded. A failure mode with a Pending or None recommendation starts **Undecided**, with the toggle in a middle position;
selecting it chooses Evaluate, and selecting it again chooses Exclude. Resting the pointer on the toggle shows its state, such as "Exclude — toggle on
to evaluate". Decisions save as soon as they are made.

The **Status** column shows what each failure mode still needs:

- **Undecided**: no decision yet.
- **Add rationale** (amber): the failure mode is excluded and needs a rationale. Selecting it opens the rationale dialog.
- **DST rationale**: excluded with DST's rationale only. Selecting it opens the dialog to read it or add the team's own.
- **Rationale**: excluded with the team's own rationale.
- **Review change** (on an amber row): DST changed its recommendation after the team decided.

Every excluded failure mode needs a rationale. The **Exclusion rationale** dialog shows the failure mode's name, **DST rationale (read-only)** when
DST supplied one, or **No screening recommendation** with DST's note when it made none, and a **User rationale** box of up to 4,000 characters for
the team's reason. **Save** stores it and **Cancel** closes the dialog. A DST rationale alone satisfies the requirement.

The page messages list each failure mode still undecided ("1 failure mode needs an Evaluate or Exclude decision.") and each exclusion without a
rationale, for example "PFM 08 - CLE due to Desiccation Cracking at the Crest is excluded from evaluation without a rationale." These are required
inputs (see [Page Messages](./040-working-in-dst.mdx#page-messages)).

## Recommendation changes

When later inputs change DST's recommendation for a failure mode the team has already decided, its row turns amber and its status reads **Review
change**. <FigReference figKey="dst-users-guide-fig-failure-mode-selection-review-change" /> shows the review.

Selecting **Review change** opens a popover that states the change, for example "DST recommendation changed: Exclude → Evaluate", and the team's
decision. **Keep** keeps the decision and **Switch to** changes it; either one confirms the review. Until the team confirms it:

- the page messages list "PFM 08 - CLE due to Desiccation Cracking at the Crest: DST now recommends Evaluate (was Exclude). Use Review change on its
  row to confirm your decision." (with the failure mode's number and name; the clause in parentheses appears when there was an earlier
  recommendation);
- the failure mode's rows on the Failure Mode Evaluation page read **Needs confirmation**, and its failure mode pages cannot be opened (see
  [Opening a location](./341-locations.mdx#opening-a-location));
- the failure mode is left out of the risk analysis.

## User-defined failure modes

The **User Defined** group holds failure modes the team adds itself. **Add failure mode** adds a row with the box "Name this failure mode, then
click away to save"; the name, up to 200 characters, saves when the user leaves the box, and an empty name adds nothing. DST numbers user-defined
failure modes after the catalog. A user-defined failure mode has no DST recommendation. DST adds it set to Evaluate; switching it to Exclude needs a rationale.

The pencil icon (**Rename**) on a user-defined row edits its name in place; Enter or leaving the box saves it. The trash icon (**Remove**) opens the
dialog "Remove PFM 28?" (with the failure mode's number), which warns that the failure mode "and any evaluation data entered for it will be
permanently deleted. This cannot be undone." **Remove** deletes it and **Cancel** keeps it.

:::caution

Removing a user-defined failure mode deletes it and its evaluation data permanently.

:::

## Verifying the selection

The screening team verifies the page as a whole with the verification badge in the sub-navigation bar (see
[Human Verification](./040-working-in-dst.mdx#human-verification)). DST clears its verification when the team changes a decision or rationale,
or adds, renames or removes a user-defined failure mode. It also clears it when DST adopts a first-time Evaluate recommendation, when a
recommendation changes for a failure mode in evaluation, and when a change on the Dam Data or Dam Information page changes which failure modes
apply.
