# Working in DST

Use this page to learn how every screening page works: moving between modules and pages, how entries save and results calculate, reading page
messages, entering tables, verifying pages, submitting for review, and what to do when inputs are locked or another user changes the same data. The
pages that follow describe each page's own inputs and refer back here for everything shared.

## Navigation

Every screening page shares the site header, the module navigation and the sub-navigation bar.

### The site header

The site header appears on every signed-in DST page:

- The USACE castle logo and **Home** return to the Dashboard.
- **Resources** links to the RMC Website, the National Inventory of Dams, the USACE Dam Safety Program and FEMA Dam Safety.
- **Help** opens **About the DST**, the **User's Guide**, **FAQs**, the **Change Log**, which lists what changed in each release of DST, and **Terms &
  Conditions**.
- The bell opens the **Notifications** list, and its badge counts unread notifications. Selecting a notification marks it read and opens the page it
  concerns; × dismisses it. **Mark all read** and **Dismiss all** act on the whole list.
- The avatar opens a menu with the user's name, email address and role, **View Profile** (see
  [The Profile Page](./030-getting-started.mdx#the-profile-page)) and **Logout**. Users with administrative or meeting management duties see further
  items here, and a badge on the avatar counts items awaiting their attention.

The **Feedback** button on every page reports a problem or suggestion to the DST administrators (see [Feedback](#feedback)).

### Modules and pages

Selecting a module in the module navigation opens its first page, and the sub-navigation bar lists that module's pages. Selecting a page in the
sub-navigation opens it. **Screening Management** appears only for the screening's Facilitator and administrators. The Review module opens on
Submission Readiness for the Facilitator, Team Members and administrators before submission, and on Review Levels for Viewers and after submission; a
reviewer lands on the level the reviewer is active on.

Some pages open a single item, such as a failure mode location from the Failure Mode Evaluation page or a level from the Review Levels page. The
sub-navigation then shows a breadcrumb, for example **Failure Mode Evaluation › PFM-01 · Left Abutment**; selecting the page name returns to it. The
browser tab shows the page name and the screening name, which helps tell screenings apart in separate tabs.

**Collapse navigation**, beside the screening name, shows the module navigation as icons only; a module's name appears when the pointer rests on its
icon, and **Expand navigation** restores it. When the sub-navigation bar has no room for every page, the remaining pages appear in a **More** menu,
whose dot turns amber when a page in it needs verification. On a phone, **Open navigation** lists every module and the current module's pages, and the
current page's name opens a list of the module's other pages.

### Who else is on the page

When other users have the same screening open, their initials appear in circles in the sub-navigation bar. Resting the pointer on a circle shows the
user's name, marked **(Facilitator)** for the Facilitator, and the page that user is viewing; a **+N** circle lists any further users. Seeing another
user on the same page is a cue to coordinate before editing the same inputs (see [Editing Conflicts](#editing-conflicts)). The circles are not shown on
phones.

## Saving

DST saves every entry automatically; pages that hold screening inputs have no Save button:

- **Text and number fields** save when the user leaves the field, by pressing Tab or selecting elsewhere on the page.
- **Selections**, such as drop-down lists, check boxes, toggles and option buttons, save as soon as the user makes them.
- **Tables** save shortly after each change (see [Tables](#tables)).
- **Rich-text editors**, used for the Major Findings sections and failure mode rationales, save after the user pauses typing for two seconds, and
  again when the user leaves the editor.

When a save takes longer than a second, **Saving…** appears in the sub-navigation bar. DST shows no message when a save succeeds.

A few editors hold their changes until the user saves them: the cross-section editors have their own Save and Cancel buttons (see
[Saving and Canceling](./311-cross-section-editors.mdx#saving-and-canceling)). Leaving the cross-section editors, the Inundation Geometry page or the
Consequence Data page with unsaved changes, or the Results Data page with rows that could not be saved, asks for confirmation; **Stay** keeps the page
open, and **Leave Page** discards the changes.

:::caution
Saving an entry can make results on other pages out of date. DST then clears those results, says so in a notice, and clears the verification of the
affected pages (see [Human Verification](#human-verification)).
:::

## Automatic Calculation

Results on most pages calculate automatically: each calculation starts once every input it needs is complete and valid, and runs again whenever one of
those inputs changes. The Consequences module's HEC-RAS and LifeSim runs are the exception and are started by the user (see
[Consequences](./400-consequences.mdx)). While a calculation runs, the affected chart or result shows that it is updating.

When an input changes after results were calculated, DST clears the out-of-date results and explains what changed, for example "Dam Information or
Flood Hazard inputs changed since these results were calculated. The results, nodal adjustments, and SRP verification were cleared; the analysis will
recalculate automatically." A notice may also ask for a new selection, such as when a cross section a result depended on has been deleted.

The calculations depend on separate calculation services. If a service cannot be reached, the pages that depend on it show the site alerts icon (see
[Site alerts](#site-alerts)) with a message such as "The calculation service is currently unavailable. PFM calculations are temporarily unavailable."
Inputs still save, and the calculations run once the service returns.

The button shows three counts:

- **Errors** (red): inputs that are invalid, such as values out of order.
- **Warnings** (amber): advisories that point out something worth checking. They never block anything.
- **Required inputs** (blue): inputs the page still needs.

Resting the pointer on the button summarizes the counts, for example "1 error, 1 required input", or reads "No messages on this page". Selecting it
opens the list. A message about another page ends with a **Go to** link naming that page.

Messages never stop the user from typing, saving or moving between pages, and they update each time the page saves. Errors and required inputs
usually must be resolved before submission, but each page's Submission Readiness tile applies that page's own completeness checks, which can differ from
its messages (see [Submission Readiness](#submission-readiness)). Pages without a page messages button report warnings and errors as notices instead.

DST also marks individual inputs:

- A table cell whose value causes an error is tinted red. A cell holding text that is not a number is also tinted, and that entry is saved as blank.
- A **Required** tag beside a field's label marks an input the page needs.
- An empty justification box shows the note **Justification required** beside its title until the user types in it. A missing justification leaves the
  page Incomplete on the Submission Readiness page.

### Site alerts

Site alerts report a problem that affects DST, either published by the DST administrators or raised by DST when a service it depends on is
unavailable or unreliable. On a screening page, an alert that applies to the page appears as an icon in the sub-navigation bar: red for an urgent
alert, amber for a warning. Resting the pointer on the icon lists the alerts, and selecting it opens them with any links they carry. The icon
disappears when the alert ends. On the Dashboard and the Profile page, site alerts appear at the top of the page, and an alert with an × can be
dismissed until the page next loads.

## Tables

Curves and other series of values are entered in tables that work like a spreadsheet:

- **Selecting and editing.** Selecting a cell and typing replaces its value. Dragging, or Shift with a second cell, selects a range; Ctrl+click adds
  cells to the selection. **Delete** clears the selected cells.
- **Moving between cells.** The Up and Down arrow keys move between rows. Tab and Shift+Tab move between editable cells. Pressing Tab in the last cell
  adds a new row, as long as the last row holds a value.
- **Pasting.** A block copied from a spreadsheet pastes into the table starting at the selected cell, and the table adds rows as needed. Tables with a
  fixed set of rows paste only what fits.
- **Copying.** Ctrl+C copies the selected cells, and Ctrl+A selects every cell.
- **Toolbar.** The buttons above the table add, insert and delete rows, select all cells, copy the selection with or without its column headers, and
  paste. Resting the pointer on a button shows its name. Tables with a fixed set of rows hide the row commands.

Table entries save shortly after each change, and the table's messages arrive with the save.

:::tip
To enter a long curve, copy its columns from a spreadsheet, select the first cell of the table and press Ctrl+V; the table adds the rows it needs.
:::

## Charts

Most pages plot what is entered or calculated on them. The charts share these behaviors:

- **Reading values.** Resting the pointer on a chart shows the values at that point, for every series at the same position. Selecting a series in the
  chart's key hides or shows it.
- **Zooming and panning.** On charts of curves and series, such as the Operational Data curves, the hazard curves, the stage time series and the system
  response charts, the mouse wheel (or a pinch on a touch screen) zooms around the pointer, and dragging the plot pans it. A chart never zooms or pans
  past the extent of its data.
- **Reset zoom.** Once a chart is zoomed, the **Reset zoom** button returns it to its full extent. Zooming is not saved, and leaving the page resets it.
- **Downloading.** Charts whose data can be exported have a **Download as CSV file** button, which saves the plotted values as a CSV file.

## Summary Tray

Use the summary tray to enter a page's notes and justifications and to attach supporting documents. Dam Data, Operational Data, Flood Hazard, Stage
Duration, Seismic Hazard and each failure mode page have one. Collapsed, the tray is a strip at the bottom of the page with its title, such as
**Operational data summary**, and a status, such as "No notes yet"; the status turns amber when something in the tray needs attention, such as a
missing justification. <FigReference figKey="dst-users-guide-fig-working-in-dst-summary-tray" /> shows a tray open at half height.

## Human Verification

A member of the screening team verifies each page that holds entered data, attesting that the data on the page is accurate. Every page must be
verified before the screening can be submitted for review. <FigReference figKey="dst-users-guide-fig-working-in-dst-verification" /> shows a page
before and after verification.

<Figure
  figKey="dst-users-guide-fig-working-in-dst-verification"
  src="figures/web-applications/dst/users-guide/v1.0/figures/working-in-dst-verification.png"
  alt="The Screening Information sub-navigation bar twice. Before verification, Dam Data and Operational Data have amber dots and the badge reads Unverified in amber. After verification, Operational Data has a green dot, Dam Data keeps its amber dot, and the badge reads Verified in green, with the tooltip 'Verified by Jordan Hale on Nov 20, 2026'."
  caption="The Operational Data page before (top) and after (bottom) verification."
  width="100%"
/>

- **Verifying.** The user selects the amber **Unverified** badge. There is no confirmation dialog; DST shows a notice such as "Operational Data
  verified." and the badge becomes a green **Verified** label. Resting the pointer on it shows who verified the page and on what date. On a phone the
  badge is a round shield button that opens a panel with a **Verify page** button.
- **Who can verify.** The Facilitator, Team Members and administrators, while the screening's inputs are open for editing.
- **Edits clear verification.** Changing any input on a verified page returns it to Unverified, and so can results that DST clears because an input
  changed elsewhere.
- **Tab dots.** The dot after a page name is amber when the page needs verification and green when it is verified. A page with several verifiable
  parts, such as Failure Mode Evaluation with one entry for each failure mode location, shows green only when every part is verified. A page with
  nothing to verify has no dot.

resolution period, so the team can respond to review comments. Inputs also lock while a screening has no Facilitator. While inputs are locked, a strip
at the top of every page explains why (<FigReference figKey="dst-users-guide-fig-working-in-dst-input-lock" />), every input is read-only and table
cells turn gray. <TableReference tableKey="dst-users-guide-table-working-in-dst-input-lock" /> lists the strips.

## Editing Conflicts

Several team members can work in a screening at once. When two users change the same record, DST keeps the first save, reloads the page with the
latest data, and tells the second user, usually with "This record was modified by another user. Your page has been refreshed." The second user's
conflicting entry is not kept; the user enters it again if it is still wanted. A conflict when verifying Operational Data, Flood Hazard, Stage
Duration or Seismic Hazard reloads the page's data and leaves the page unverified, with a warning such as "This record was modified by another user.
Reload the page and try again."; the user checks the updated data and verifies again. Watching who else is on the page (see
[Who else is on the page](#who-else-is-on-the-page)) helps the team avoid conflicts.

## Comments

During review, reviewers leave comments on the page they concern. A reviewer on the active review level sees an **Add a review comment** button on each
page during the review period, which opens a comment panel. [Adding Comments](./700-review.mdx#adding-comments) describes commenting, team responses
and backcheck.

## Feedback

Use the **Feedback** button to send a problem report or suggestion to the DST administrators without leaving the page. It opens the **Send feedback**
panel, and the page stays in use while the panel is open, so the user can set up what to capture. The panel has two views, **New report** and **My
reports**, and × closes it. <VideoReference videoKey="dst-users-guide-video-working-in-dst-feedback" /> shows the panel.

- **Type** (required): **Bug** ("Something broke or behaved unexpectedly."), **Result looks wrong** ("A calculated value seems incorrect."),
  **Confusing** ("You weren't sure what to do or what something meant.") or **Suggestion** ("Ideas about how the site looks, reads or works: layout,
  wording, workflow."). The type also changes the prompt in **What happened**.
- **Severity**: **Blocking** (the user cannot continue), **Major** (work can continue, but something important is wrong or needs a workaround) or
  **Minor** (a small problem that does not affect the work or results). It defaults to Minor, and "If a result might be wrong, choose at least Major."
  Confusing and Suggestion reports take no severity.
- **Summary** (required): one line, up to 120 characters.
- **What happened** (required): up to 4,000 characters.
- **Screenshots and videos** (optional): up to 5 files of up to 25 MB each. **Capture page** takes a screenshot of the current browser tab, **Record
  clip** records the tab for up to 20 seconds, and **Upload** attaches PNG, JPG or WebP images and MP4, WebM or MOV videos. Images can also be pasted
  or dropped into the panel. Only the shared tab is captured, and only the user and the DST administrators can see the attachments.

DST adds technical details, such as the browser and the DST version, automatically. A **Result looks wrong** report also attaches the data the page had
loaded. **Submit report** becomes available once the required fields are complete and every attachment has
finished uploading.

**My reports** lists the user's reports, open ones first, each with its status: New, Acknowledged, Fixed, Won't fix, Duplicate or Can't reproduce. A
report the DST team has answered shows their note.
