# Working in DST

Every page inside a screening shares the same navigation and the same rules for saving, calculating, reporting problems and verifying data. This
chapter describes those shared behaviors once. The chapters that follow describe each page's own inputs and refer back here for everything common to
all pages.

## Navigation

### The site header

The site header appears on every DST page. The USACE castle logo and **Home** return to the Dashboard. **Resources** lists the RMC Website, the
National Inventory of Dams, the USACE Dam Safety Program and FEMA Dam Safety, each opening an external site. **Help** includes the **Change Log**,
which lists what changed in each release of DST, and **Terms & Conditions**.

The bell opens the **Notifications** list, with **Mark all read** at the top. An amber badge on the bell counts unread notifications. The avatar
shows the user's initials and opens a menu headed by the user's name, email address and role, with **View Profile** and **Logout**. Users with
administrative duties see further items in this menu, and an amber badge on the avatar counts items awaiting their attention.

### Modules and pages

The module navigation on the left lists the eight modules of the screening. Selecting a module opens its first page, and the sub-navigation bar across
the top of the page lists that module's pages. Selecting a page in the sub-navigation opens it. The browser tab shows the page name and the screening
name, so several screenings or pages can be told apart when open in separate tabs.

The button beside the screening name, **Collapse navigation**, narrows the module navigation to icons only, leaving more room for the page; a module's
name then appears when the pointer rests on its icon. **Expand navigation** restores it. DST remembers the choice on that computer.

### Tablets and phones

DST adapts its navigation to the width of the screen:

- **Laptop and desktop screens** show the full layout in <FigReference figKey="dst-users-guide-fig-working-in-dst-screening-page" />.
- **Tablet screens** keep the sub-navigation bar but always show the module navigation as icons only.
- **Phone screens** replace the module navigation with a menu button, **Open navigation**, at the left of the sub-navigation bar. It opens a panel
  listing every module, with the current module's pages beneath it. The sub-navigation bar uses shortened page names, such as **Operational** for
  Operational Data.

### Who else is on the page

When other users have the same screening open, their initials appear in circles at the right of the sub-navigation bar, before the verification
badge. Resting the pointer on a circle shows the user's name, role and the page that user is viewing. Up to four circles appear; beyond that, a
**+N** circle lists the rest. Seeing another user on the same page is a cue to coordinate before editing the same inputs (see
[Editing Conflicts](#editing-conflicts)).

## Saving

DST saves every entry automatically. There is no Save button on any page that holds screening inputs:

- **Text and number fields** save when the user leaves the field, by pressing Tab or selecting elsewhere on the page.
- **Selections** — drop-down lists, check boxes, toggles and option buttons — save as soon as the user makes them.
- **Tables** save shortly after each change (see [Tables](#tables)).
- **Rich-text editors**, used for the Major Findings sections and failure mode rationales, save after the user pauses typing for two seconds, and
  again when the user leaves the editor.

When a save takes longer than a second, **Saving…** appears with a spinner at the right of the sub-navigation bar. DST shows no message when a save
succeeds. The cross-section editors are the one exception to automatic saving; they have their own Save and Cancel buttons, described in Chapter 8,
Cross-Section Editors. The Inundation Geometry and Consequence Data pages warn with an **Unsaved Changes** dialog if the user tries to leave while
an entry there has not yet been saved.

Saving an entry may change other pages. When the change makes earlier results out of date, DST clears those results and says so in a notice, and
any verification of the page is cleared (see [Human Verification](#human-verification)).

## Automatic Calculation

DST has no Calculate or Run buttons. Each calculation starts on its own once every input it needs is complete and valid, and runs again whenever one
of those inputs changes. While a calculation runs, the affected chart or result shows that it is updating.

When an input changes after results were calculated, DST clears the out-of-date results and shows a notice explaining what changed — for example,
that Dam Information or Hydrologic Hazard inputs changed, that the results were cleared, and that the analysis will recalculate automatically. A
notice may also ask the user for a new selection, such as when the cross section or material a result depended on has been deleted.

The calculations depend on separate calculation services. If a service cannot be reached, a dismissible alert appears at the top of the affected
pages, such as "The calculation service is currently unavailable. PFM calculations are temporarily unavailable." Inputs still save while a service is
unavailable, and the calculations run once it returns.

The banner holds up to three cards, one per severity:

- **Required Inputs** (light blue) lists inputs the page still needs.
- **Warnings** (amber) are advisories. They point out something worth checking but do not block anything.
- **Errors** (red) list inputs that are invalid.

Required inputs and errors must be resolved before the screening can be submitted for review (see
[Submission Readiness](#submission-readiness)); warnings never prevent submission. A message about another page ends with a **Go to** link to that
page. Messages never stop the user from typing, saving or moving between pages, and they update each time the page saves. On a page without a
banner, warnings and errors appear instead as notices in the corner of the screen.

DST also marks individual inputs:

- A table cell whose value causes an error is tinted red. A cell holding text that is not a number is also tinted, and that entry is saved as
  blank.
- A **Required** tag beside a field's label marks an input the page needs.
- A justification box that is still empty shows an amber outline and the note **Justification required** beside its title. The note clears as the
  user types. Missing justifications are listed on the Submission Readiness page rather than in the page banner.

## Tables

Curves and other series of values are entered in tables that work like a spreadsheet:

- **Selecting and editing.** Selecting a cell and typing replaces its value. Dragging, or selecting one cell and then another with Shift held,
  selects a range; Ctrl-click adds cells to the selection. **Delete** clears the selected cells.
- **Moving between cells.** The Up and Down arrow keys move between rows. Tab and Shift+Tab move between editable cells. Pressing Tab in the last cell
  adds a new row, as long as the last row holds a value.
- **Pasting.** A block copied from a spreadsheet pastes into the table starting at the selected cell, and the table adds rows as needed. Tables with a
  fixed set of rows keep their rows and paste only what fits.
- **Copying.** Ctrl+C copies the selected cells. Ctrl+A selects every cell.
- **Toolbar.** The icon buttons above the table add, insert and delete rows, select all cells, copy the selection with or without its column headers,
  and paste. Resting the pointer on a button shows its name. Tables with a fixed set of rows hide the row commands.

Table entries save shortly after each change, and the table's messages arrive with the save.

## Human Verification

Each page that holds entered data is verified by a member of the screening team, who attests that the data on the page is accurate. Verification
is required before the screening can be submitted for review. <FigReference figKey="dst-users-guide-fig-working-in-dst-verification" /> shows a
page before and after verification.

- **Verifying.** The amber **Unverified** badge at the right of the sub-navigation bar is a button. A single selection verifies the page; there is no
  confirmation. The badge turns into a green **Verified** label, and resting the pointer on it shows who verified the page and on what date.
- **Who can verify.** The Facilitator and Team Members can verify while the screening's inputs are open for editing. For anyone else the badge is
  unavailable, with the explanation "Only screening team members can verify this page." A page may also hold off verification while it is still
  collecting data, such as Stage Duration while its reservoir data downloads.
- **Edits clear verification.** Changing any input on a verified page clears its verification, and the badge returns to Unverified. Calculations
  that DST clears because an input changed elsewhere can clear a page's verification too.
- **Tab dots.** The dot after a page name in the sub-navigation is amber when the page needs verification and green when it is verified. A page that
  holds several verifiable parts, such as Failure Mode Evaluation with one entry for each failure mode location, shows a green dot only when every
  part is verified. A page with nothing to verify has no dot.

a Testing screening ("Testing screenings cannot be submitted for review."). Submitting is a single, final step:

## Input Lock

A screening's inputs lock when it is submitted for review and stay locked through completion. They unlock only while the active review level is in
its resolution period, so the team can respond to review comments. While inputs are locked, a strip across the top of every page explains why
(<FigReference figKey="dst-users-guide-fig-working-in-dst-input-lock" />), every input is read-only, and table cells turn gray.

## Editing Conflicts

Several team members can work in a screening at once. When two users change the same record and the second save arrives after the first, DST keeps
the first save, reloads the page with the latest data, and shows a notice to the second user — usually "This record was modified by another user.
Your page has been refreshed." The second user's conflicting entry is not kept and must be entered again if it is still wanted. Seeing other users on
the page (see [Who else is on the page](#who-else-is-on-the-page)) helps the team avoid conflicts.

## Comments

During review, reviewers leave comments directly on the page they concern. A reviewer on the active review level sees a round **Add a review
comment** button at the bottom right of each page during the review period; it opens a comment panel beside the page. Commenting, team responses and
backcheck are described in Chapter 27, Review.
