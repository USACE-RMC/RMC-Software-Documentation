# Working in DST

Every page inside a screening shares the same navigation and the same rules for saving, calculating, reporting problems and verifying data. This
chapter describes those shared behaviors once. The chapters that follow describe each page's own inputs and refer back here for everything common to
all pages.

## Navigation

Every screening page shares the site header, the module navigation and the sub-navigation bar.

### The site header

The site header appears on every signed-in DST page. The USACE castle logo and **Home** return to the Dashboard. **Resources** lists the RMC Website,
the National Inventory of Dams, the USACE Dam Safety Program and FEMA Dam Safety, each opening an external site. **Help** lists **About the DST**,
**User's Guide**, **FAQs**, the **Change Log**, which lists what changed in each release of DST, and **Terms & Conditions**.

The bell opens the **Notifications** list. An amber badge on the bell counts unread notifications. Each notification shows its message and how long
ago it arrived; selecting it marks it read and opens the page it concerns, and × dismisses it. **Mark all read** and **Dismiss all** act on the whole
list, which reads "You're all caught up" when it is empty.

The avatar shows the user's initials and opens a menu headed by the user's name, email address and role, with **View Profile** (see
[Chapter 3, Getting Started](./03-getting-started.mdx#the-profile-page)) and **Logout**. Users with administrative or meeting management duties see
further items in this menu, and an amber badge on the avatar counts items awaiting their attention.

A **Feedback** button in the lower left corner of every page opens a panel for reporting a problem or suggestion to the DST administrators. On phones
and tablets it shrinks to an icon.

### Modules and pages

The module navigation on the left lists the eight modules of the screening. Selecting a module opens its first page, and the sub-navigation bar across
the top of the page lists that module's pages. Selecting a page in the sub-navigation opens it. **Screening Management** appears in the sub-navigation only
for the screening's Facilitator and administrators. The Review module is the one exception to opening on the first page: before the screening is
submitted, it opens on Submission Readiness for the Facilitator, Team Members and administrators, and on Review Levels for Viewers. After submission
it opens on Review Levels, and a reviewer lands on the level the reviewer is active on.

Some pages open a further level, such as a single failure mode location from the Failure Mode Evaluation page or a single level from the Review Levels
page. The sub-navigation then shows a breadcrumb: the page name, an arrow, and the name of the item open, for example
**Failure Mode Evaluation › PFM-01 · Left Abutment**. Selecting the page name returns to it.

The browser tab shows the page name and the screening name, so several screenings or pages can be told apart when open in separate tabs. Outside the
production site, the tab also names the environment, for example **Dam Screening Tool Test**.

The button beside the screening name, **Collapse navigation**, narrows the module navigation to icons only, leaving more room for the page; a module's
name then appears when the pointer rests on its icon. **Expand navigation** restores it. On laptop and desktop screens DST remembers the choice on
that computer.

### Tablets and phones

DST adapts its navigation to the width of the screen.

- **Laptop and desktop screens** (1,024 pixels wide or more) show the layout in
  <FigReference figKey="dst-users-guide-fig-working-in-dst-screening-page" />.
- **Tablet screens** (640 to 1,023 pixels) show the module navigation as icons. **Expand navigation** opens the full navigation over the page; it
  closes again when the user selects a page, presses Escape or selects outside it.
- **Tablet and larger screens** move any pages that do not fit in the sub-navigation bar into a **More** menu at its end. The current page always
  stays in view, and a dot on **More** turns amber when any page in the menu needs verification. Where space is tight, the current page shows a
  shortened name, such as **Operational** for Operational Data, with the full name when the pointer rests on it.
- **Phone screens** (narrower than 640 pixels) replace both navigation bars with a single bar. **Open navigation** at the left opens a panel listing every module, with
  the current module's pages beneath it. Beside it, the current page's name opens a list of the other pages in the module. The site alerts icon, the
  page messages button and the verification badge, shown as a round shield button, sit at the right. The phone bar shows neither the other users on the page nor **Saving…**.

### Who else is on the page

When other users have the same screening open, their initials appear in circles near the right end of the sub-navigation bar. Resting the pointer on
a circle shows the user's name, marked **(Facilitator)** for the Facilitator, and the module and page that user is viewing. Up to four circles
appear; when more than four users are present, three circles appear with a **+N** circle that lists the rest. Seeing another user on the same page
is a cue to coordinate before editing the same inputs (see [Editing Conflicts](#editing-conflicts)). The circles are not shown on phones.

## Saving

DST saves every entry automatically. There is no Save button on any page that holds screening inputs:

- **Text and number fields** save when the user leaves the field, by pressing Tab or selecting elsewhere on the page.
- **Selections** — drop-down lists, check boxes, toggles and option buttons — save as soon as the user makes them.
- **Tables** save shortly after each change (see [Tables](#tables)).
- **Rich-text editors**, used for the Major Findings sections and failure mode rationales, save after the user pauses typing for two seconds, and
  again when the user leaves the editor.

When a save takes longer than a second, **Saving…** appears with a spinner in the sub-navigation bar. DST shows no message when a save succeeds.

A few editors hold their changes until the user saves them. The cross-section editors have their own Save and Cancel buttons, described in
[Chapter 9, Cross-Section Editors](./09-cross-section-editors.mdx#saving-and-canceling). If the user tries to leave the cross-section editors, the Inundation Geometry page or the Consequence Data page with changes not
yet saved, or the Results Data page with rows that could not be saved, DST asks for confirmation; **Stay** keeps the page open, and **Leave Page**
discards the changes.

Saving an entry may change other pages. When the change makes earlier results out of date, DST clears those results and says so in a notice, and
any verification of the page is cleared (see [Human Verification](#human-verification)).

## Automatic Calculation

Results on most pages calculate automatically: each calculation starts on its own once every input it needs is complete and valid, and runs again
whenever one of those inputs changes. The Consequences module's HEC-RAS and LifeSim runs are the exception and are started by the user (see
[Chapter 31, Consequences](./31-consequences.mdx)). While a calculation runs, the affected chart or result shows that it is updating.

When an input changes after results were calculated, DST clears the out-of-date results and shows a notice explaining what changed — for example,
"Dam Information or Flood Hazard inputs changed since these results were calculated. The results, nodal adjustments, and SRP verification were
cleared; the analysis will recalculate automatically." A notice may also ask the user for a new selection, such as when the cross section a result
depended on has been deleted.

The calculations depend on separate calculation services. If a service cannot be reached, the pages that depend on it show the site alerts icon
(see [Site alerts](#site-alerts)) with a message such as "The calculation service is currently unavailable. PFM calculations are temporarily
unavailable." Inputs still save while a service is unavailable, and the calculations run once it returns.

The button always shows three counts, from top to bottom:

- **Errors** (red) — inputs that are invalid, such as values out of order.
- **Warnings** (amber) — advisories. They point out something worth checking but do not block anything.
- **Required inputs** (blue) — inputs the page still needs.

Resting the pointer on the button summarizes the counts, for example "1 error, 1 required input", or reads "No messages on this page". When a count
rises, its symbol pulses briefly. Selecting the button opens the list of messages under a heading for each severity. A message about another page ends
with a **Go to** link naming that page.

Errors and required inputs usually must be resolved before the screening can be submitted for review, but each page's Submission Readiness
tile applies that page's own completeness checks, which can differ from its messages (see [Submission Readiness](#submission-readiness)). Warnings
never prevent submission. Messages never stop the user from typing, saving or moving between
pages, and they update each time the page saves. Pages without a page messages button report warnings and errors instead as notices in the lower right
corner of the screen.

DST also marks individual inputs:

- A table cell whose value causes an error is tinted red. A cell holding text that is not a number is also tinted, and that entry is saved as
  blank.
- A **Required** tag beside a field's label marks an input the page needs.
- A justification box that is still empty shows an amber outline and the note **Justification required** beside its title. The note clears as the
  user types. A missing justification leaves the page Incomplete on the Submission Readiness page.

### Site alerts

DST administrators publish site alerts, and DST raises its own alerts when a service it depends on is unavailable or unreliable. On a screening page,
an alert that applies to the page appears as an icon at the right of the sub-navigation bar: a red symbol for an urgent alert, an amber one for a
warning. Resting the pointer on the icon lists the alerts, and selecting it opens them with any links they carry. These alerts cannot be dismissed;
the icon disappears when the alert ends. On the Dashboard and the Profile page, site alerts appear instead as a colored band at the top of the page. There, an alert with an × can be
dismissed; it returns the next time the page loads.

## Tables

Curves and other series of values are entered in tables that work like a spreadsheet:

- **Selecting and editing.** Selecting a cell and typing replaces its value. Dragging, or selecting one cell and then another with Shift held,
  selects a range; Ctrl+click adds cells to the selection. **Delete** clears the selected cells.
- **Moving between cells.** The Up and Down arrow keys move between rows. Tab and Shift+Tab move between editable cells. Pressing Tab in the last cell
  adds a new row, as long as the last row holds a value.
- **Pasting.** A block copied from a spreadsheet pastes into the table starting at the selected cell, and the table adds rows as needed. Tables with a
  fixed set of rows keep their rows and paste only what fits.
- **Copying.** Ctrl+C copies the selected cells. Ctrl+A selects every cell.
- **Toolbar.** The icon buttons above the table add, insert and delete rows, select all cells, copy the selection with or without its column headers,
  and paste. Resting the pointer on a button shows its name. Tables with a fixed set of rows hide the row commands.

Table entries save shortly after each change, and the table's messages arrive with the save.

## Summary Tray

Several pages gather their notes, justifications and supporting documents in a summary tray at the bottom of the page: Dam Data, Operational Data,
Flood Hazard, Stage Duration, Seismic Hazard and each failure mode page. Collapsed, the tray is a strip along the bottom of the page that shows its
title, such as **Operational data summary**, and a status, such as "No notes yet". The status turns amber when something in the tray needs
attention, such as a missing justification. <FigReference figKey="dst-users-guide-fig-working-in-dst-summary-tray" /> shows a tray open at half height.

- **Opening and closing.** Selecting the strip opens the tray at half height over the lower part of the page; the page above it stays in use.
  Selecting the header again, selecting × or pressing Escape closes the tray. The tray reopens at the height it last had.
- **Full height.** The **Full height** button (its name shows when the pointer rests on it) expands the tray over the whole page, and the same
  button, now named **Half height**, returns it. At full height the page behind the tray
  cannot be used until the tray returns to half height or closes.
- **Sections.** Each section has a title, a short description, and a **Required** or **Optional** tag where one applies. Text boxes in the tray save
  when the user leaves them, like any other text field (see [Saving](#saving)).

Every tray ends with a **Supporting documents** section (see [Supporting Documents](./06-documents.mdx#supporting-documents)). The other
sections belong to the page, and the page's own chapter describes them.

## Human Verification

A member of the screening team verifies each page that holds entered data, attesting that the data on the page is accurate. Verification is
required before the screening can be submitted for review. <FigReference figKey="dst-users-guide-fig-working-in-dst-verification" /> shows a
page before and after verification.

- **Verifying.** The amber **Unverified** badge at the right of the sub-navigation bar is a button. A single selection verifies the page; there is no
  confirmation dialog, and DST shows a notice such as "Operational Data verified." The badge turns into a green **Verified** label, and resting the pointer on it shows who verified the page and on what date. On a
  phone the badge is a round shield button; it opens a panel that shows the page's status and, for an unverified page, a **Verify page** button.
- **Who can verify.** The Facilitator, Team Members and administrators can verify while the screening's inputs are open for editing. For anyone else the badge is
  unavailable, with the explanation "Only screening team members can verify this page." A page may also hold off verification while it is still
  collecting data, such as Stage Duration while its reservoir data downloads.
- **Edits clear verification.** Changing any input on a verified page clears its verification, and the badge returns to Unverified. Calculations
  that DST clears because an input changed elsewhere can clear a page's verification too.
- **Tab dots.** The dot after a page name in the sub-navigation is amber when the page needs verification and green when it is verified. A page that
  holds several verifiable parts, such as Failure Mode Evaluation with one entry for each failure mode location, shows a green dot only when every
  part is verified. A page with nothing to verify has no dot.

## Input Lock

A screening's inputs lock when it is submitted for review and stay locked through completion. They unlock only while the active review level is in
its resolution period, so the team can respond to review comments. Inputs also lock while a screening has no Facilitator. While inputs are locked, a
strip across the top of every page explains why (<FigReference figKey="dst-users-guide-fig-working-in-dst-input-lock" />), every input is read-only,
and table cells turn gray. <TableReference tableKey="dst-users-guide-table-working-in-dst-input-lock" /> lists the strips.

## Editing Conflicts

Several team members can work in a screening at once. When two users change the same record and the second save arrives after the first, DST keeps
the first save, reloads the page with the latest data, and shows a notice to the second user — usually "This record was modified by another user.
Your page has been refreshed." The second user's conflicting entry is not kept and must be entered again if it is still wanted. A conflict when verifying
Operational Data, Flood Hazard, Stage Duration or Seismic Hazard does not refresh the page; DST reports "This record was modified by another user.
Reload the page and try again." Seeing other users on the page (see [Who else is on the page](#who-else-is-on-the-page)) helps the team avoid
conflicts.

## Comments

During review, reviewers leave comments directly on the page they concern. A reviewer on the active review level sees a round **Add a review
comment** button at the bottom right of each page during the review period; it opens a comment panel beside the page. [Chapter 34, Review](./34-review.mdx#comments),
describes commenting, team responses and backcheck.
