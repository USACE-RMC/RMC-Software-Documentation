# Git Conventions

Reference file for git-related skills.

## Commit Messages

- Start with action verbs: Add, Update, Fix, Remove, Refine, Rework, Merge
- Concise and descriptive (one line preferred, multi-line body for complex changes)
- Do NOT include "Co-Authored-By" or any AI attribution
- No conventional commits prefix (feat:, fix:) — plain English
- Focus on the "why" more than the "what"

### Recent examples from this project

```
Overhaul color scheme from teal to steel blue with tokenized surfaces
Redesign homepage with teal gradient product tiles and frosted glass icons
Add figure reference popovers, nowrap references, and CSS refinements
Resolve LifeSim User's Guide v1.0 Level 3 QC findings
```

## Branch Naming

An administrator assigns every PR a review lane using `/review classify`.
Changed content determines the appropriate classification; branch names are descriptive.

### Documentation branches (changes under `docs/`)

These prefixes describe intent and do not assign or advance a review lane.

- `docs/new/{slug}` — new document (Peer → Lead Civil → Technical edit in the Content PR; separate Director review after draft merge)
- `docs/major/{slug}-v{X.0}` — major revision (Peer → Lead Civil → Technical edit)
- `docs/minor/{slug}-v{X.Y}` — minor revision (Peer → Technical edit)
- `docs/fix/{slug}` — editorial fix (no review; admin self-merge)
- `docs/dev/{slug}` — dev docs under `docs/dev/` (no review; admin self-merge)

### Non-documentation branches (components, plumbing, styling, scripts, CI)

Administrators assign the `code` lane to changes without document edits. It has no
formal review stages, but both `CI Build` and `review-workflow` must pass before administrator merge.

- `feature/{descriptive-name}` — new components, new site capabilities, enhancements
- `fix/{descriptive-name}` — bug fixes in components, styles, scripts, build tooling
- `chore/{descriptive-name}` — dependency bumps, refactors, config, cleanup
- `ci/{descriptive-name}` — GitHub workflows and repository automation

Use `feature/` rather than `enhancement/`; older branches used the latter.

A PR mixing document content and site code is a specialized administrator-classified
case. Authors should change only one document per PR; a branch prefix grants no exception.

## Pull Requests

- Title: Short, action-verb-first, under 70 characters
- Body format:
  ```
  ## Summary
  - Bullet point 1
  - Bullet point 2
  ```
- **No "Test plan" section** — keep the body to Summary only
- **No AI attribution** — do not mention Claude, AI, or include "Generated with" footers
- Base branch: `main`
- Always create from a feature/fix branch, never from main

## Safety Rules

- Never force push to `main` or `master`
- Never use `--no-verify` to skip hooks
- Prefer new commits over `--amend` (amend only when user explicitly asks)
- Never auto-commit without user confirmation
- Stage specific files by name, never `git add -A` or `git add .`
- Never commit `.env`, credentials, or secrets

## Auto-Generated Files

These files are regenerated by build scripts and should generally not be committed manually:
- `sidebars.js`
- `src/reportIdMap.js`
- `static/counters/` contents
- `static/versions/` contents
- `src/data/` contents
